## 一、整体设计

### 1.1 这套方案要解决什么

让云台上固定的摄像头始终把「人」保持在画面中心。

云台是二自由度舵机云台：

| 轴 | 机械行程 | 舵机 | 驱动 | 引脚 |
|---|---|---|---|---|
| 左右旋转 yaw | 0 ~ 270° | 270° 舵机（圆盘底座） | TIM1_CH4 | PA11 |
| 上下俯仰 pitch | 0 ~ 180° | 180° 舵机（立式） | TIM1_CH1 | PA8 |

以上按「视觉云台系统」PCB（STM32F103C8T6 最小系统板插在排母上）的实际接线，
完整引脚依据见 `引脚分配.md`。板上其余资源：K230 串口 USART2（**PA3=RX / PA2=TX**，
115200，RXNE 中断 + 256 字节环形缓冲）；板间通信 USART1 **PA9=TX / PA10=RX 双向**，接收侧收到的循迹板调试文本原样转发给蓝牙 USART3（PB10/PB11）
（30 ms 发一帧 13 字节），**PA10 虽已引出但本工程未配置**；蜂鸣器 **PB4**
（3V3/PB4/GND）目前**只有引脚宏、没有驱动**；OLED 的 PB12(SCL)/PB13(SDA) 宏保留，
但**这块板上没有 OLED 座**，要用需飞线。

### 1.2 为什么用「位置式 PID」而不是增量式

控制目标是**误差归零**：人偏在画面某侧 → 云台转过去 → 人回到中心 → 误差为 0。

```
correction = Kp*e + Ki*Σe + Kd*(e - e_last)/dt      [度]
yaw_angle = yaw_angle + correction × deg_per_unit
```

关键点：**输出是角度的增量修正，不是绝对角度**。

如果写成 `angle = PID(e)`，那么误差为 0 时 PID 输出也是 0，云台会往 0 度跑，
永远归不了零。必须保留「当前角度」作为基准，误差为 0 时修正量为 0，云台才停在原地。

### 1.3 代码分层

```
application/gimbal_task.c     ← 应用逻辑：串流程、节流刷屏
        ↓
modules/vision_protocol.c     ← 协议解析：13 字节 → 归一化偏差
modules/gimbal_controller.c   ← 控制律：低通/死区/PID/限幅
modules/oled.c                ← 显示
        ↓
bsp/bsp_uart.c                ← USART2 + 环形缓冲（唯一碰 USART2 的地方）
bsp/bsp_servo_pwm.c           ← TIM1 双通道 PWM（唯一碰 TIM1 的地方）
bsp/bsp_soft_i2c.c            ← GPIO 开漏电平（唯一碰 OLED 引脚的地方）
        ↓
Drivers/（CMSIS + ST 标准外设库）
```

依赖方向严格单向：`application -> modules -> bsp -> 寄存器`。

### 1.4 与需求文档的对应

《实验室学习项目》的「(1) 基础要求 → 云台人体跟踪」：

> 云台由两个舵机控制（水平 + 俯仰）；摄像头采集图像，识别人体，输出人体在画面中的坐标；
> STM32 根据坐标偏差调节舵机角度，使人保持在画面中心。

本工程完整实现这一条。需求文档里的循迹、电机、模式切换、超声测距、蜂鸣器
属于另一块主控（`Chassis_2026`），本工程**不实现也不预留**。

## 二、数据流

```
K230D BOX
  camera → YOLOv5n 人体检测 → 取最大人体框中心 (cx, cy)  [像素, 1280×960]
        │
        │  UART2 115200，每 30 ms 一帧
        ▼
  [13 字节帧] AA 55 01 08 | cx(int16 大端) | cy(int16 大端) | 0 | 0 | XOR
        │
        ▼
STM32 USART2 (PA3) --RXNE 中断--> 环形缓冲 256 B
        │
        ▼  GimbalTask_Loop() 每 10 ms
  Vision_Poll()
    ① 滑窗找 4 字节帧头（失配只前进 1 字节）
    ② 凑够 13 字节
    ③ 前 12 字节异或校验
    ④ 通过则出队；cx/cy < 0 视为「本帧无人」
    ⑤ 像素偏差 → 归一化偏差（画面半边 = 100）
        │
        ▼
  GimbalController_Update()
    ① 目标是否新鲜（300 ms 超时）  —— 不新鲜：保持角度并返回
    ② 一阶低通 filt += (raw-filt)×0.3
    ③ 乘方向符号 sign_x / sign_y
    ④ 软死区（|e|≤3.0 置 0，否则扣掉死区段）
    ⑤ 位置式 PID
    ⑥ angle += correction × deg_per_unit
    ⑦ 行程限幅（yaw 3~267，pitch 3~177）
        │
        ▼
  BSP_Servo_SetYawDeg / SetPitchDeg
    角度 → 脉宽（0°=500us，满量程=2500us）→ 夹到 [500,2500] → TIM1 CCR
        │
        ▼
  PA11 / PA8 → 舵机（云台下 / 云台上）
```

### 2.1 发给循迹板的另一条支路（模式 2 用）

除驱动舵机外，控制器还每 30 ms 把「云台 yaw 偏角」发到 USART1：

```
  GimbalController_GetYawDevTenthDeg()
     = (yaw_angle_deg - GIMBAL_CHASSIS_ZERO_DEG) × 10   [0.1 度, 标定值, 默认 135]
        │
        ▼
  LinkProtocol_Send()  → 13 字节帧，type = 0x02
        │
        ▼
  BSP_Link_SendBuffer() → USART1 TX → PA9 → 循迹板 PA10
```

**为什么发偏角而不是画面偏差**：云台一直把人保持在画面中心，
画面偏差恒接近 0，不携带方向信息；而「云台转了多大角度去对准人」
正好编码了人相对车头的方位。详见 `../../docs/双板分工与协议.md`。

**无论有没有人都要发**（无人时 `flags.bit0 = 0`）：
停发会让循迹板无法区分「没人」和「断线」。

**三个时间尺度**（理解抖动的关键）：

| 环节 | 周期 |
|---|---|
| K230 发帧 | 30 ms |
| **控制环** | **10 ms** |
| 刷 OLED | 100 ms |
| 串口回传 | 500 ms |

30 ms 一帧、10 ms 一拍 → **同一个偏移值会被连续用 3 拍**。
不滤波的话云台每 3 拍跳一次（33 Hz 台阶感）；低通就是用来抹平这个台阶的。

## 三、各子系统实现

### 3.1 `bsp/bsp_uart.c` — K230 串口

- 中断接收 + 256 字节环形缓冲（实际可用 255，永远留一个空位区分空/满）。
- 缓冲满时**丢弃新字节**，不覆盖未解析数据（覆盖会让帧结构彻底错乱）。
- 提供 `PeekAt` / `Skip` 两个「只看不出队」的接口，供上层做滑窗重同步。
- ISR 只做「读寄存器 + 写缓冲 + 清标志」，几微秒内返回。
  115200 下字节间隔 87 us，ISR 里做任何耗时操作都会丢字节。

### 3.2 `modules/vision_protocol.c` — 协议解析

从 `Gimbal_1.0/Vision.c` 移植，**算法未改**。三个设计要点：

1. **失配时只前进 1 字节**，不是跳过整帧。
   如果缓冲区里是 `AA 55 AA 55 01 08 ...`（前面多了一组帧头），
   跳整帧会把真帧头跳过去，永远同步不上。

2. **没找到帧头时保留末尾 3 个字节**（帧头长度 - 1）。
   防止帧头恰好跨在两次调用之间被丢掉。

3. **校验失败也只丢 1 字节**。
   残帧里可能就藏着下一帧的帧头，只能慢慢挪。

> 该解析器已用真实 `Vision.c` 在 PC 上做过 20 项测试（含 100 帧连续、
> 堆 3 帧、前面混垃圾、中间丢 1 字节、错位帧头 `AA AA 55`），全部通过。

`frame_count` / `last_ms` 对**丢失帧也更新**（它们表示链路是否有数据）；
判断有没有人必须看 `detected`。

### 3.3 `modules/gimbal_controller.c` — 控制律

从 `Gimbal_1.0/Gimbal.c` 移植，数学与参数未改，只重命名与分层。

**软死区**而不是「小于 d 就置 0」：

```c
if (e >  d) return e - d;
if (e < -d) return e + d;
return 0;
```

原因：置 0 的写法在边界不连续，微分项 `Kd*(e-e_last)/dt` 会把跳变放大成一次冲击
（实测单拍约 0.21°，是软写法的 5 倍）。软写法输出从 0 平滑增长，
死区内行为完全一样（都是 0）。

**丢失目标时保持角度**：不累加、不盲转、不回中。
人短暂遮挡后重新出现，云台还在原位，能立刻接上。

### 3.3.1 限位反向扫视（2026-11-19 新增）

**要解决的问题**：模式 1 循迹时车在跑、人站着不动，车绕到某个方位后，
人的方位角超出云台可用行程（264 度），云台顶在 3 度或 267 度上，
摄像头再也看不到人 —— 而「丢失就保持不动」的旧策略会让它**永远**停在端点等。

**做法**：目标丢失且云台顶在端点时，以固定角速度朝**反方向**扫，
扫到另一端折回来，直到重新看到人；扫够若干单程仍没找到就回中点放弃。

```
丢失 800 ms（兜底，2026-11-20 新增）
或 丢失 + 贴端点(±5°) 连续 300 ms
        ↓  进入扫视，朝"离开端点"的方向
   45 度/秒 匀速扫
        ↓  到另一端 -> 单程数 +1、换向
   单程数 = 6（3 个来回）仍没人 -> 回上电中点、退出
        ↓  期间任何一帧检测到人
   立即退出扫视、清积分与微分历史、恢复正常 PID
```

**参数**（`config/gimbal_config.h`）：

| 宏 | 值 | 含义 |
|---|---|---|
| `GIMBAL_SWEEP_SPEED_DEG_S` | 45.0f | 扫视角速度（45°/s ⇒ 每帧转 1.35°，远小于 65° 视场，不会漏人） |
| `GIMBAL_SWEEP_CONFIRM_MS` | 300U | 贴端点持续多久才认定「撞死」 |
| `GIMBAL_SWEEP_TRIGGER_MS` | 800U | 丢人多久后无条件开始扫（从最后一帧算起）；因为云台丢人就停住、走不到端点 |
| `GIMBAL_SWEEP_EDGE_DEG` | 5.0f | 距端点多少度以内算「贴边」（2026-11-19 由 1.5 放宽，端点是软限位、舵机逼近时会回弹，1.5 太严难以触发） |
| `GIMBAL_SWEEP_PASSES` | 6U | 单程数，6 = 3 个来回（单程 264÷45 ≈ 5.9 s） |
| `GIMBAL_BOOT_GRACE_MS` | 8000U | 上电后禁止扫视的时间窗（K230 启动要 5~15 s 才出第一帧） |
| `GIMBAL_SWEEP_NEED_TARGET` | 1U | 必须曾跟踪到人一次才允许扫视，避免空场景/摄像头没起来时乱扫 |

**三个设计取舍**：

1. **只在「丢失」时扫，不在「跟踪但贴边」时扫** —— 人还在画面边缘时贴边是正常现象，
   此时反向扫会主动把人甩出去。
2. **贴边要连续 300 ms 才认定** —— 车体加减速时云台会被惯性带到端点附近，
   单拍贴边就触发会导致误扫。
3. **扫够次数回中点** —— 否则人真的在盲区（264+65 差 31 度的那段）时，
   云台会一直来回扫，白耗电、还顶着限位。

**已知副作用**：扫视期间 `IsTracking()` 为 0，发给底盘的 `flags` bit0 也是 0。
模式 1 的底盘不读链路，无影响；**模式 2 会把「云台在扫视」误判成「丢人」而进搜索**。
若以后要在模式 2 用，需要给 `flags` 加一位 `bit1 = 云台正在扫视`，
让底盘收到时只走直线、不进搜索。

### 3.4 `bsp/bsp_servo_pwm.c` — 舵机 PWM

- **TIM1**（高级定时器，挂在 **APB2**，时钟宏 `RCC_APB2Periph_TIM1`）：
  72 MHz / 72 = 1 MHz 计数（PSC = 72-1），ARR = 20000-1 → 20 ms（50 Hz），
  因此比较寄存器值**就是脉宽微秒数**（1 计数 = 1 us）。
- 两个通道：**PA8 = TIM1_CH1 = 云台(上) 俯仰 180°**、
  **PA11 = TIM1_CH4 = 云台(下) 左右旋转 270°**（用户已按实物确认，不是推断）。
- ⚠️ **TIM1 是高级定时器，必须调 `TIM_CtrlPWMOutputs(TIM1, ENABLE)` 打开 MOE**，
  否则 PA8/PA11 上永远没有波形——现象是「代码全对、示波器全平」。
  这是从通用定时器换到 TIM1 最容易漏的一步（通用定时器没有 MOE 概念）。
- 角度 → 脉宽：`500 + 角度/满量程 × 2000`，两个舵机满量程不同
  （yaw 270°，pitch 180°）。
- 使能 CCR 预装载，改值时在下一个周期生效，避免畸形脉冲。
- **最后一层限幅**：脉宽夹到 [500, 2500] us。
  正常路径上控制器已按行程夹过角度，这里是防御性冗余，
  保证绝不因参数写错而输出超范围脉宽。

### 3.5 `application/gimbal_task.c` — 应用逻辑

串起「收帧 → 控制 → 输出」，并按 100 ms / 500 ms 节流刷屏与回传。
节流是必须的：刷一次 OLED 要 3~5 ms、串口回传一行约 5 ms，
放进 10 ms 控制节拍会直接拖垮控制周期。

### 3.6 OLED 布局

```
Yaw:135
Pit: 90
X:+12 Y:-05
St:LOCK  1234
```

第 3 行显示的是**低通后、乘符号与过死区之前**的原始偏差。
所以「屏幕上还有数字」不代表控制环在用它（可能在死区内被置 0）。

> **硬件现状**：「视觉云台系统」PCB 上**没有 OLED 座**。`pin_config.h` 里的
> PB12(SCL) / PB13(SDA) 宏仍然保留，这两个脚在闲置排针上；要显示必须飞线
> 3V3 / GND / SCL / SDA。不接线时 OLED 初始化只在这两个空脚上做开漏输出，
> 不影响控制。

### 3.7 `modules/link_protocol.c` — 双板链路发送

- 每 30 ms 组一帧 13 字节（`type = 0x02`）发给循迹板，负载是
  `yaw_dev_tenth_deg` / `offset_x` / `distance_cm` / `flags`。
- 与 K230 帧**同结构、只有 type 不同**，两侧共用同一套解析思路，降低出错概率。
- 负载结构定义成 `LinkPayload_t` 由调用方填，模块本身不依赖控制器 ——
  这样它只依赖 `bsp_uart_link.h`（纯接口），可以直接在 PC 上编译做单元测试。
- 阻塞发送约 1.1 ms（13 字节 @115200），因此由 `gimbal_task` 节流调用。

### 3.8 `bsp/bsp_bt_uart.c` — 蓝牙转发（USART3）

**用途**：把循迹板那路 500 ms 一行的调试文本，通过 JDY-31 蓝牙模块无线送到电脑，
省掉拖着长线跑车时「边跑边看串口」。

**数据通路（本板只做搬运，不解析）**

```
循迹板 PA9 --115200--> 云台板 PA10(USART1_RX)
    → s_rx_buf[256] 环形缓冲
    → GimbalTask_ForwardChassisText()（每拍最多搬 64 字节）
    → s_tx_buf[256] 发送环（入队，几十纳秒）
    → TXE 中断搬运 → USART3_TX(PB10) → JDY-31 → 电脑蓝牙虚拟串口
```

**为什么发送必须用中断**：一行约 110 字节，@115200 阻塞发送 110×87 us ≈ **9.5 ms**，
而控制环周期是 **10 ms** —— 阻塞会让舵机 PWM 晚一拍、肉眼可见抖动。所以
`BSP_BT_SendByte()` 只入队并打开 TXE 中断，真正的串口搬运在 ISR 里，每次 1 字节。

**队列满怎么办**：丢新字节，返回 0。**绝不在主循环里等** —— 蓝牙没连上（没人收）时
日志丢了无所谓，舵机卡一拍就是抖动。`BSP_BT_GetTxPending()` 可用来诊断
「是不是一直在丢」（持续接近 256 就说明对端没在收）。

**为什么选 PB10/PB11**：它们是 USART3 默认映射，不需要 AFIO 重映射；且在闲置排针 A 组上，
与 TIM1（PA8/PA11）、USART2（PA2/PA3）、USART1（PA9/PA10）、蜂鸣器（PB4）都不冲突。

**模块侧要求**：JDY-31 出厂 9600，必须 `AT+BAUD8` 改成 115200 并断电重启，
否则收到的全是乱码。配置脚本：`tests/jdy31_at.py`。


### 3.8.1 蓝牙命令解析（`modules/bt_command.c`）

模块职责：把 JDY-31 收到的一行文本翻译成命令码，交给 `gimbal_task.c` 下发。

| 项 | 说明 |
|---|---|
| 入口 | `BtCommandEvent_t BtCommand_Poll(void)`，每拍调一次，无命令时 `command = BT_CMD_NONE` |
| 返回值 | `{command, argument}`；只有 `yaw`/`pitch` 用得到 `argument`（单位 度） |
| 行结束 | CR 或 LF |
| 字符过滤 | 只收 `0x20~0x7E`；出现其它字符（乱码、断线残留）整行作废 |
| 归一化 | 去空格/制表符 → 转大写 |
| 关键字 | `MODE1`/`M1` → 1，`MODE2`/`M2` → 2，`STOP`/`S` → 3，`YAW <度>` → 4，`PITCH <度>`/`PIT <度>` → 5 |
| 数字解析 | 手工解析，不用 `strtof`（避免链入浮点转换库）；支持负号与小数，分隔符用 `:`、`=` 或空格都可省 |
| 行长度 | `BT_CMD_LINE_MAX` = 20，超长作废 |

两类命令的落地方式不同：

- `mode1`/`mode2`/`stop`（码 1/2/3）**下发给底盘**：借链路帧第 11 字节（原 reserved），
  并连发 `GIMBAL_BT_CMD_HOLD_FRAMES`（5 帧 = 150 ms）防单帧丢失；底盘按边沿检测，只会执行一次。
  云台板回 `CMD:<原文> OK` 加 CRLF。
- `yaw <度>`/`pitch <度>`（码 4/5）**只在本板执行**：直接调 `GimbalController_SetAngle()`
  把云台摆到指定角度（另一轴保持不动，超出行程由控制器夹紧），不写进链路帧
  （底盘不认 4/5，也没必要知道）。回执给的是夹紧后的真实角度，如 `YAW:200.0 OK` 加 CRLF。

为什么需要手动摆位：标定零点、实测镜头视场、复核行程限位、录演示视频都要把云台停在某个确切角度，
以前只能改代码重烧；现在手机发一条 `yaw 200` 即可，且不依赖视觉链路（人丢了也能用）。

## 五、安全层

| 场景 | 当前行为 | 位置 |
|---|---|---|
| **视觉丢失**（K230 发 -1/-1） | 保持当前角度不动，OLED 显示 LOST | `gimbal_controller.c` 第 1 步 |
| **K230 断线/死机** | 300 ms 超时后同上（依赖毫秒时基正常） | `vision_protocol.c` / `Delay.c` |
| **角度越界** | 夹到行程上下限，顶住不继续推 | `gimbal_controller.c` 第 7 步 |
| **脉宽越界** | 夹到 [500, 2500] us | `bsp_servo_pwm.c` 末层冗余 |
| **上电瞬间** | 立即输出行程中点脉宽，避免舵机因无信号松掉乱甩 | `bsp_servo_pwm.c` Init 末尾 |
| **参数写错** | `Init` 时对初始角度再夹一次 | `gimbal_controller.c` Init |
| **看门狗** | ❌ **未启用** | 见「优化空间」 |

**上电默认状态**：yaw 135°、pitch 90°（都在行程中点），
对应脉宽 1500 us，云台正对前方。

**积分饱和**：当前 `Ki = 0`，不存在积分饱和；若以后启用 `Ki`，
必须在行程限幅处同步实现「输出饱和时停止积分」，否则顶限位后会猛弹。

## 六、踩过的坑

### 6.1 轴名与物理轴错位，导致「人左右走云台却上下点头」

**现象**：人左右移动，动的是上下俯仰舵机。

**根因**：旧代码 `angle_on` 名叫 on（俯仰），实际接的是左右旋转舵机；
`angle_down` 反着来。命名与物理轴交叉，靠名字猜必错。

**修复**：迁移时改用物理轴命名 `yaw_angle_deg` / `pitch_angle_deg`，
并把「画面 x → yaw、画面 y → pitch」写进注释与文档。

**以后如何避免**：名字必须描述物理量，且每个轴只保留一处「方向/映射」定义点。

### 6.2 舵机行程写反，把 180° 舵机推到机械死点

**现象**：上下方向转到极限时舵机堵转、发热。

**根因**：`Servo_SetAngle_On` 用 `/180`、`Down` 用 `/270`，与实物相反。

**修复**：按实物确认「立式=180°、圆盘=270°」，公式与行程限幅成套修改。

**以后如何避免**：角度公式的分母与行程限幅必须成对维护，写在同一个 config 里。

### 6.3 位置式 PID 的微分项被 `/dt` 放大 100 倍

**现象**：`Kd = 0.3` 时云台大幅摆动。

**根因**：位置式里微分项是 `Kd * (e-e_last) / dt`，`dt = 0.01` 等于放大 100 倍；
`Kd = 0.3` 实际增益 30 倍，把检测框抖动和 30 ms 台阶放大成大幅摆动。

**修复**：`Kd` 降到 0.01（等效增益 1），摆动消失。

**以后如何避免**：位置式的积分要 `×dt`、微分要 `÷dt`，两者方向相反，
调参时先算等效增益再动手。

### 6.4 毫秒时基不递增，断线保护失效

**现象**：K230 拔线后云台不显示 LOST，继续用旧坐标。

**根因**：`Delay_us` 每次都会重装并清零 SysTick，所以「读 `VAL` 差值」恒为 0，
毫秒时钟只在上电后跳一次。于是 300 ms 超时判断恒成立。

**修复**：时基改为在 `Delay_us` 内部按延时长度记账，`Delay_GetMs()` 返回累计值。

**以后如何避免**：不要用「被反复重装的计数器」推算流逝时间；
时间基准要么用独立定时器中断，要么在延时函数里自己记账。

### 6.5 方向符号反复取反导致正反馈

**现象**：云台越追越偏、撞限位卡死。

**根因**：改了轴映射后 `sign` 的交叉关系变了，两个轴的符号同时翻了一次。

**修复**：两个 `sign` 一起取反。

**以后如何避免**：判据只能是「偏差是否收敛到 0」，
不能是「云台转向是否符合直觉」——摄像头在云台上，两者视角相反。

## 七点五、参数命令：`set` / `get` / `dump` / `reset`（2026-11-20 新增）

云台板在这里扮演**中间人**：手机发文本，它翻译成 0x03 二进制帧发给底盘，
再把底盘回的 0x04 翻译成一行短文本回给手机。

### 7.5.1 数据通路

```
手机 --(蓝牙 SPP)--> JDY-31 --> USART3 --> 云台板 bt_command
                                              |
                                        0x03 帧（USART1）
                                              v
                                          循迹板 params.c
                                              |
                                        0x04 帧
                                              v
                        云台板 link 解复用 --> 蓝牙回 "SG:6"
```

### 7.5.2 为什么 USART1 上要做「解复用」

同一条串口线上混着两种东西：循迹板每 1 s 打印的 ASCII 调试行（`C: mode=...`），
以及 13 字节二进制帧。二者混发时如果都当文本转发，二进制帧会变成乱码；
都当二进制解析，调试文本会被吞掉。

判据很简单：**二进制帧一定以 `0xAA` 开头，ASCII 文本永远不会有 0xAA**。
所以 `GimbalTask_ForwardChassisText()` 按首字节分流：不在帧内且不是 `0xAA`
就原样转给蓝牙，是 `0xAA` 就攒满 13 字节、校验通过且 `type == 0x04` 才当应答处理。

### 7.5.3 回显格式（刻意做短）

| 情况 | 回显 |
|---|---|
| 成功 | `SG:6` |
| 参数名不认识 | `ERR:1 id` |
| 越界 | `ERR:2` |
| 只读 | `ERR:3` |
| 底盘未就绪 | `ERR:4` |
| 复位 | `RESET OK` |
| `save`（未实现） | `ERR:4 noflash` |

短是为了手机屏一行放得下；`dump` 时 13 个参数各回一行。

## 八、必须遵守的设计规范

1. `application/` **禁止**直接调用 `GPIO_*` / `TIM_*` / `USART_*` 等外设库函数；
2. 所有物理量单位必须写进变量名或注释（`_deg` / `_px` / `_ms` / `_s`）；
3. 禁止魔法值，参数集中在 `config/`；
4. 控制输出必须限幅：角度有两级（行程 + 脉宽），不得绕过 BSP 直接写 CCR；
5. 每个轴只允许**一个**方向修正点（`GIMBAL_SIGN_X/Y`），不得在别处再取反；
6. `GIMBAL_CONTROL_PERIOD_MS` 与 `GIMBAL_CONTROL_DT_S` 必须同步修改；
7. 舵机行程与 `BOARD_SERVO_*_FULL_SCALE_DEG` 必须成对修改；
8. 修改公共接口、控制参数、安全逻辑后必须同步更新本文档。

## 3.8.3 参数短名表（2026-11-21 增至 18 个）

`dump` 现在输出 **18 行**，顺序按 id 0~17：

### 3.8.4 蜂鸣器（`bsp/bsp_buzzer.c` + `modules/buzzer.c`，2026-11-21）

- **硬件**：云台板 J3 = 3V3 / PB4 / GND，板上三极管驱动**有源**蜂鸣器 → PB4 给高电平即响（`bsp_buzzer.c` 顶部 `BOARD_BUZZER_ACTIVE_HIGH` 可一键取反）。
- **BSP 层**只做三件事：`Init`（推挽输出 + 上电静音）、`On`、`Off`。
- **模块层**是节奏播放器：音型用「段」表描述（每段 = 时长 ms + 电平），`Buzzer_Step()` 每 10 ms 推进一步。
- **为什么不阻塞**：长鸣 1 s 若用 `Delay_ms`，舵机会在 1 秒内完全失控。现在它被切成 100 个小步，控制环照常跑。
- **接口**：`Buzzer_Init/Play/Step/IsPlaying/SetEnabled/IsEnabled`；`Buzzer_Play` 会打断正在播放的音型。
- **触发源**：底盘经 `0x05` 帧遥控（见 `docs/双板分工与协议.md` 5.8）。

| 音型号 | 事件 | 节奏 | 总时长 |
|---|---|---|---|
| 0 | 起跑 | 嘀—嘀 | 280 ms |
| 1 | 过十字 | 嘀 | 80 ms |
| 2 | 丢线/丢人 | 嘀嘀嘀 | 300 ms |
| 3 | 到停车线 | 长鸣 | 1000 ms |
| 4 | 断链 | 长鸣 | 500 ms |
| 5 | 低电压 | 嘀 | 100 ms |

#### 3.8.4.1 蜂鸣器开关（2026-11-21）

两层：

1. **上电默认值**：`config/gimbal_config.h` 的 `GIMBAL_BUZZER_ENABLE`（1 = 上电允许发声，0 = 静音），`Buzzer_Init()` 读它。改这个要**重烧云台板**才生效。
2. **运行期开关**：蓝牙文本命令（本板本地执行，不跨板、不发帧）

| 手机发 | 回显 | 说明 |
|---|---|---|
| `bz off` | `BZ:OFF` | 立即静音（正在播的也停） |
| `bz on` | `BZ:ON` | 恢复发声 |
| `bz` | `BZ:ON` / `BZ:OFF` | 只查询，不改状态 |

为什么两层：彩排时 `bz off` 保持安静，正式比赛重新上电按常量（默认开）自动恢复，不会因为"上次静音了"导致比赛没声音。

实现位置：`modules/bt_command.h` 的 `BT_CMD_BEEPER = 12`、`modules/bt_command.c` 的 `ParseParamCmd()` 里匹配 `BZ`、`application/gimbal_task.c` 的命令分派里调 `Buzzer_SetEnabled()` 并回显。
